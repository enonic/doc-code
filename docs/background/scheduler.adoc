= Scheduler
:toc: right
:imagesdir: images

The scheduler runs <<tasks#, named tasks>> at a time, at an interval, or on a cron schedule, in a cluster or on a single node.

== Scheduled jobs

A scheduled job names a task by its descriptor, the `config` to run it with, the user to run it as, and a calendar that says when. Jobs are stored in the system repository and survive restarts. They are created, listed, modified and deleted through the <<../libraries/lib-scheduler#, scheduler library>>, or created from the platform's https://developer.enonic.com/docs/platform/stable/config/system#scheduler[scheduler configuration file]. The full shape of a job is the <<../libraries/lib-scheduler#scheduled_job, ScheduledJob>> type.

== Calendars

A job's calendar has a `type` and a `value`, whose format depends on the type. The exact rules for each are in the <<../libraries/lib-scheduler#schedule-type, Schedule>> type.

[#one-time]
=== One-time

Runs once, at an instant in UTC. A time already in the past runs as soon as the job is created. The job stays afterwards, with `lastRun` recording that it is done, so its name cannot be reused to run it again. image:xp-810.svg[XP 8.1.0,opts=inline] Where the name is used for a single occasion, `deleteAfterRun: true` removes the job once its task has been submitted.

[source,typescript]
----
{type: 'ONE_TIME', value: '2021-01-01T10:30:00.00Z', deleteAfterRun: true}
----

[#cron]
=== Cron

Runs at the calendar positions a https://www.unix.com/man-page/linux/5/crontab[UNIX cron] expression names, in the given time zone. Use it for work that has to happen at a particular time of day.

[source,typescript]
----
{type: 'CRON', value: '0 5 * * *', timeZone: 'GMT+2:00'}  // 05:00 every day
----

[#fixed-rate]
=== Fixed rate

image:xp-810.svg[XP 8.1.0,opts=inline] Runs at an interval, given as an ISO-8601 duration and measured between the starts of two runs. Use it for work that belongs at an interval rather than at a time of day. The interval is not anchored to the clock and does not survive a restart or a move to another node, so the next run may shift by up to one interval.

[source,typescript]
----
{type: 'FIXED_RATE', value: 'PT5M'}  // every five minutes
----

== Where jobs run

Exactly one node in a cluster runs the scheduler at a time, chosen among the nodes that allow it. The platform's https://developer.enonic.com/docs/platform/stable/config/system#scheduler[`acceptScheduling`] setting excludes a node, typically the master nodes. The scheduling node only submits the tasks; each task then runs on any node that has the application providing it and <<tasks#distributable, accepts distributable tasks>>.

[#non-overlap]
image:xp-810.svg[XP 8.1.0,opts=inline] A job does not start a run while its own previous run is still going. What becomes of the run that was due depends on the calendar: a cron occurrence is skipped, since a cron occurrence is a calendar position and a missed one is missed, while a fixed-rate run waits and starts once its predecessor finishes.

WARNING: Not overlapping is best effort, not a guarantee. Two runs of the same job can still overlap when the cluster is partitioned, or when the record of the previous task is no longer available to be checked. A task that must never run concurrently with itself needs a lock of its own.

NOTE: The guarantee is per job, not per task. Several jobs may name the same descriptor, and nothing relates them - they can run at the same time as each other.

[#last-task-id]
== What a scheduled task receives

A scheduled task runs with the `config` of its job as parameters, exactly as if it had been submitted through the task API.

image:xp-810.svg[XP 8.1.0,opts=inline] It also learns which task ran for the job last, through the `schedule.lastTaskId` attribute of its <<../libraries/lib-context#, context>>. That is useful where each run continues from where the last one reached - fetching the previous run's result to process only what has changed since. The value is absent on a job's first run and on a job whose last run left no record.

.Reading the previous run's task id
[source,typescript]
----
import {get as getContext} from '/lib/xp/context';
import {get as getTask} from '/lib/xp/task';

export function run(): void {
    const lastTaskId = getContext().attributes['schedule.lastTaskId'] as string | undefined;
    const previous = lastTaskId ? getTask(lastTaskId) : null;

    if (previous) {
        log.info('Previous run: %s', previous.state);
    }
}
----

The chain only ever names tasks the scheduler let run, so an id that is there is one whose run actually happened.

== System jobs

XP ships two jobs of its own, disabled by default: vacuum, which deletes unused blobs, and audit log cleanup, which deletes old audit records. They are enabled and tuned in the platform's https://developer.enonic.com/docs/platform/stable/config/system#predefined-jobs[scheduler configuration].
