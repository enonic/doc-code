= Runtime
:toc: right
:imagesdir: ../images

What powers your Enonic app at execution time — the JVM-hosted JavaScript engine, the module system, the threading model, and the cluster-aware machinery you get for free.

== Execution model

Enonic XP runs on top of the Java Virtual Machine. Your app's TypeScript and JavaScript files are executed by an embedded JavaScript engine, with full access to the JVM through the <<java-bridge#, Java bridge>>. There is no Node.js, no separate JS process, and no inter-process bridge — server-side JS runs inside the same JVM as the platform itself.

Two engines are available:

Nashorn:: The default engine. Stable, production-ready, ships with every XP install. All XP releases since 7.x have shipped Nashorn.

GraalJS:: image:preview.svg[Preview,opts=inline] The engine that will replace Nashorn, available to try since XP 8.1.0. Implements the current ECMAScript standard. *Not for production* - see <<graaljs, GraalJS preview>>.

=== Language level

Every module runs in ECMAScript *strict mode*, on both engines.

Nashorn is *ES5* compatible, with some ES6 capabilities. Transpile to ES5 — that is what the official starters do, and what apps have always done. See <<typescript#, TypeScript>> for the build step.

image:preview.svg[Preview,opts=inline] GraalJS tracks the current ECMAScript standard, so modern syntax runs without down-levelling. Transpiling to ES5 stays the portable choice for now: an app built that way runs on either engine, which is what makes the preview something you can try and back out of.

A modern language level is not a modern *environment*, though, and that is where the expectations GraalJS raises go wrong — see <<graaljs-limits, what GraalJS does not bring with it>>.

[#graaljs]
=== GraalJS preview

image:preview.svg[Preview,opts=inline] *Not for production.* Nashorn remains the default and the supported engine; GraalJS is here to try and report on, and what follows may still change while it is in preview.

The engine is chosen *per application*, from the `+X-Script-Engine+` manifest header the application bundle declares. An application that declares none runs on Nashorn. Applications on different engines coexist in the same installation, so a single app can be moved across without touching the rest.

Code can tell which engine it got. GraalJS installs a `Graal` global, and Nashorn has no such name:

[source,typescript]
----
if (typeof Graal !== 'undefined') {
    log.info(`${Graal.language} ${Graal.versionECMAScript}`);  // JavaScript 2026
}
----

`Graal.versionECMAScript` is the year of the ECMAScript compatibility mode in force — the concrete answer to which language level you actually have. `Graal.versionGraalVM` gives the GraalVM version, and `Graal.isGraalRuntime()` reports whether the Graal compiler is optimizing hot code; where it answers `false` the engine still runs, at lower peak performance. See the https://www.graalvm.org/latest/reference-manual/js/JavaScriptCompatibility/#graal-object[Graal object] in the GraalJS compatibility reference.

[#graaljs-limits]
==== What GraalJS does not bring with it

A current-standard engine invites expectations XP does not meet. The language is modern; the environment around it is neither a browser nor Node.js.

ES modules:: *Not supported.* `import` and `export` do not work at runtime. Use `require()` and `exports`; see <<globals#esm, ECMAScript modules>>.
`async` / `await`:: *Not supported.* There is no event loop and there are no timers — no `setTimeout`, `setInterval` or `queueMicrotask` — and nothing in the platform unwraps a promise a module returns. The syntax parses, so the failure is silent: an `async` function hands its caller a `Promise` where a value is expected, and an `async` HTTP function returns that promise to the site engine in place of a response. An `await` on a promise nothing will settle leaves it pending, and execution simply carries on. Top-level `await` is a syntax error, a module body being a plain function. Write synchronous code, and move work that should not block a request into a <<../background/tasks#, task>>.
Node.js APIs:: *Not supported.* No `process`, `Buffer` or `global`, and no Node module resolution — `require()` is XP's own and resolves inside the app bundle, never `node_modules` at runtime. A dependency that reaches for any of these fails however well it bundles.
Most web APIs:: *Not supported.* No `fetch`, `URL`, `URLSearchParams`, `TextEncoder`, `atob`/`btoa`, `crypto`, `structuredClone`, `AbortController`, `XMLHttpRequest` or `localStorage`. What you get is the language itself plus `console`, `JSON`, `Intl`, `Math`, `Date`, `Map`, `Set`, `Proxy`, `Reflect`, `BigInt` and `WeakRef`. For HTTP, mail, storage and the rest, use the platform <<../libraries#, libraries>>.
Single-threaded assumptions:: *Wrong here.* The runtime is multithreaded — see <<threading, Threading>> — and an application gets a pool of script contexts rather than one. A module can be loaded more than once, and its top-level state is not a safe place to keep anything. Code written for Node's single thread, holding a cache or a counter at module level, does not behave the way its author expected.

Nothing about how you *write* an app changes: the same modules, the same libraries, the same <<java-bridge#, Java bridge>>. What changes is the execution environment around them.

*Compiled code is shared across contexts.* One engine serves the whole installation, and the code it compiles is cached across every script context built from it: a module parsed while one context starts is reused by the next, rather than parsed again for each.

*An application gets a pool of script contexts.* Contexts are created lazily as concurrency demands them, and *module-level state is per context* - two requests may load the same module and see two different copies of its top-level variables. This is the same rule <<threading, threading>> already imposes, enforced more strictly: treat top-level state as read-only, and put anything that must be shared in a repo node, the cache library, or another explicit store.

*Values cannot leave the context that created them.* A JavaScript function or object belongs to one script context and is meaningless in another. This is what makes <<../libraries/lib-task#executefunction, `executeFunction()`>> unsupported on GraalJS: it hands a function to another execution. Submit a <<../background/tasks#, named task>> with `submitTask()` instead.

*Disposers must be registered during start-up.* Register `+__.disposer+` from `main.ts`, or from a module it loads while starting. A registration made later - from a component implementation the first time it is loaded, say - is ignored and logged. See <<java-bridge#disposer, `+__.disposer+`>>.

TIP: Run your test suite against both engines before switching a production app. The differences above are the ones the platform imposes; a dependency written against Nashorn's language level can have its own.

== Modules and bundling

Each `.ts` or `.js` file in your app is a module under the https://wiki.commonjs.org/wiki/Modules/1.1[CommonJS module specification]. Modules export values via `exports`, and consume other modules via `require()` — `import` and `export` statements are not supported at runtime, on either engine, see <<globals#esm, ECMAScript modules>>. Paths are rooted at the app bundle, not the filesystem — `require('/lib/greet')` loads `src/main/resources/lib/greet.ts` from the same app.

Platform libraries are referenced by name (for example, `require('/lib/xp/content')`). See <<functions#modules_and_the_bundle, Functions: Modules and the bundle>> for the full path-resolution rules and bundle boundaries.

TypeScript is supported as the authoring language; the build step transpiles to JavaScript before deployment. See <<typescript#, TypeScript Definitions>>.

== Loading and caching

XP loads each module *once per app deploy* and caches it. Subsequent `require()` calls and subsequent triggers reuse the cached module — the file is not re-read or re-parsed. Top-level code in a module therefore runs exactly once per deploy.

NOTE: On GraalJS — a image:preview.svg[Preview,opts=inline] preview engine, *not for production* — the unit is the script context: a module is loaded once per context, so its top-level code runs once for each context the application is given. Everything below still holds, and applies with more force — there can now be several copies of a module's top-level state. See <<graaljs, GraalJS preview>>.

This makes module top-level a natural place for one-time setup (requiring libraries, computing constants), but a poor place for mutable state. Treat anything declared outside a function body as immutable after load. For state that must survive between invocations, use a repo node, the `cache` library, or another explicit persistence mechanism.

See <<functions#loading_and_caching, Functions: Loading and caching>> for the implications on each function type.

[#threading]
== Threading

The runtime is multithreaded. The platform serves requests, dispatches events, and runs background tasks concurrently across multiple threads, taking advantage of multi-core CPU architectures. There is no single event loop — each request, task, or event listener runs on a worker thread from a managed pool.

Two consequences for your code:

* *Module-level state is shared across threads.* Cached modules are visible to every thread executing within the app. If two requests both call `require('/lib/cache')`, they receive the same module instance. Treat top-level state as read-only.
* *Implementations are reentrant.* A function may be invoked concurrently with itself. Don't accumulate state in module-level variables across invocations.

== Clustering

XP can run as a single node or as a cluster of nodes sharing the same data. The runtime is cluster-aware out of the box:

* *Events* fire across the cluster. A listener registered on any node receives events published from any other node. See <<events#, Events>>.
* *Scheduled jobs* are distributed. A scheduled job runs on one cluster node per fire — XP coordinates so the same job doesn't execute twice. See <<../background/scheduler#, Scheduler>>.
* *Repositories* are replicated. Content writes propagate to all nodes; reads can target any node.

Apps deployed to a cluster are installed and started on every node. The runtime guarantees the same module-loading and caching semantics on each node — your app sees a consistent execution environment regardless of which node serves a given request.

== What you get for free

Apps run inside a fully equipped platform. The runtime gives you, without extra setup:

* *Persistence* — content, nodes, repositories, blobs, all queryable and clusterable.
* *HTTP routing* — the <<../web/request-response#, Portal>> dispatches incoming requests to four services (`/api`, `/admin`, `/site`, `/webapp`); you provide the implementations.
* *Identity & access management* — pluggable <<../web/id-providers#, ID providers>>, role-based permissions, audit logging.
* *Cluster-wide events* — see <<events#, Events>>.
* *Background work* — <<../background/tasks#, tasks>> and <<../background/scheduler#, scheduled jobs>>.
* *Localization* — see <<i18n#, Localization>>.
* *Java interop* — see <<java-bridge#, Java bridge>>.

Compatibility:: An app built against any XP release runs unchanged on every patch and minor release within the same major version. Major version upgrades are documented separately — see <<../upgrade#, Upgrading>>.
