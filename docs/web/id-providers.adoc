= Building ID Providers
:toc: right
:imagesdir: images

The XP framework offers a solution for pluggable authentication called ID providers

== Introduction
As part of the XP's Identity and Access Management (IAM) system, services may be loosely associated with an ID provider via vhost configuration.

The ID provider is responsible for providing  user authentication, independent of the source identity system.

ID providers are wired tightly into the <<../web#common_request_pipeline, common HTTP request pipeline>>.
They participate both in pipeline execution steps, and through the contextually mounted ID provider API.

This section describes how to implement an ID provider application.

TIP: Two ready-made ID providers are published on https://market.enonic.com[Enonic Market] and cover most common needs without writing code: *OIDC ID Provider* — for any OpenID Connect-compliant identity system (Auth0, Okta, Microsoft Entra, Keycloak, etc.) — and *Simple ID Provider* — a turn-key local identity store with a built-in login form. Reach for those first; implement a custom ID provider only when neither fits.

[[idprovider-endpoints]]
== Endpoints and mounting

Unlike the four <<../web#, services>>, an ID provider has no URL prefix of its own. Instead, every ID provider is reachable through a single fixed mountpoint:

`+/_/idprovider/<idprovider-name>+`

This mountpoint is *contextual* — the same `+/_/idprovider/+` space resolves within the site, webapp, and admin services (the flat `/api` endpoint has no `+/_/+` space), so an ID provider can serve its login flow and custom requests regardless of which service the user is interacting with. `+<idprovider-name>+` is the name given to the ID provider when it is configured — it is unrelated to the key of the application that implements it.

Three behaviours are reachable under the mountpoint, each invoking the matching <<#idproviderts, implementation>> function:

`+/_/idprovider/<name>/login+`:: Invokes `login` — a deterministic login endpoint, available for every provider.

`+/_/idprovider/<name>/logout+`:: Invokes `logout`.

`+/_/idprovider/<name>+`:: The base endpoint dispatches to the provider's `GET`/`POST`/… HTTP functions.

`+/_/idprovider/<name>/device/code+`, `+/_/idprovider/<name>/device+`, `+/_/idprovider/<name>/authorize+`, `+/_/idprovider/<name>/token+`, `+/_/idprovider/<name>/register+`:: image:../../images/xp-820.svg[XP 8.2.0,opts=inline] XP's own https://developer.enonic.com/docs/platform/stable/security/access-tokens[access token] endpoints, served for the provider's users when the vhost enables the `device` or `code` flow, with the OAuth metadata under `+/_/idprovider/<name>/.well-known/+`. The implementation does not serve them; it only renders the consent page, through <<#oauthconsent, `oauthConsent`>>.

Rather than hardcoding these paths, generate them with the portal library helpers — <<../libraries/lib-portal#loginurl, loginUrl()>>, <<../libraries/lib-portal#logouturl, logoutUrl()>> and <<../libraries/lib-portal#idproviderurl, idProviderUrl()>> — which resolve the correct contextual URL for the current request.

[NOTE]
====
The endpoint is *mounted* everywhere, but an ID provider only *activates* for a request when it is bound to the request's virtual host. The vhost mapping declares which ID provider(s) apply and, optionally, <<#flows, which flows>> each of them serves. See the https://developer.enonic.com/docs/platform/xp8/config/vhosts[vhost configuration] for the binding rules.
====

== Descriptor
An IDprovider application requires a descriptor file.
The descriptor should be placed in your project as `src/main/resources/idprovider/idprovider.yaml`.

.Sample idprovider.yaml
[source,yaml]
----
kind: "IdProvider"
mode: "LOCAL" # <1>
form:         # <2>
- type: "TextLine"
  name: "title"
  label: "Title"
  default: "User Login"
  occurrences:
    min: 0
    max: 1
----

<1> *mode* specifies how users and groups are process and stored in XP. Allowed values are:
+
* *LOCAL* - Users and groups are fully managed by the IDprovider (i.e. no integrations or external ID systems).
* *EXTERNAL* - Users and groups exist in a remote system. The IDprovider acts as a "broker" between XP and the remote Identity system.
* *MIXED* - Users exist in a remote system, but the groups are created and managed locally in XP.
+
<2> *form* defines config options that can be defined from the UI when setting up ID providers.
Forms are based on the https://developer.enonic.com/docs/cms/xp8/schemas[schema system]
+
NOTE: This forms does not support CMS-specific input types, such as contentSelector and htmlArea.

== idprovider.ts

Add an ID provider implementation at `src/main/resources/idprovider/idprovider.ts`. An application may only implement a single ID provider.

To implement your ID provider, export one or more of the following functions:

image:../../images/xp-820.svg[XP 8.2.0,opts=inline] Every function receives the <<request-response#request, request>>. On an ID provider's own function calls the request also carries `+request.idProviderSettings+` (<<../libraries/types#id-provider-settings, `IdProviderSettings`>>): what the virtual host serving the request declares for this ID provider in https://developer.enonic.com/docs/platform/stable/config/vhosts[`com.enonic.xp.web.vhost.cfg`], read from `+mapping.<name>.idProvider.<idp>.*+` and the mapping's `audience`. It is absent when the host does not map the ID provider.

[source,json]
----
{
  "idProviderSettings": {
    "flows": ["code", "device", "login", "logout"],  // <1>
    "audience": ["https://api.example.com"]  // <2>
  }
}
----
<1> The flows the host serves for the ID provider, sorted. Empty means no restriction on the ID provider's own flows; XP's token flows `device`, `code` and `register` are served only where listed, or on the default virtual host. An ID provider uses it to enable its own flows: the standard ID provider serves basic authentication only where `basic` is listed or the list is empty.
<2> The audiences the host is configured to serve, sorted. Empty means the host serves its own URL and XP's issuer name. The scopes a token can be asked for are the ID provider's, not the host's: see <<../libraries/lib-auth#getscopes, `getScopes()`>>.

NOTE: To serve static assets (CSS, JS, images — e.g. for a login page), use the https://developer.enonic.com/docs/lib-static[`lib-static`] library, *not* `lib-asset`. Like admin extensions, an ID provider runs in a context where `lib-asset` does not fit; `lib-static` (typically paired with `lib-router`) is designed for serving static files from here.

=== handle401
Perhaps the most common use of ID providers is handling 401 errors (Unauthorized).
When a user attempts to access a resource or service that requires authentication, the pipeline will produce an HTTP 401 response.
The IDprovider may intercept the response before this is sent to the client (browser) and perform an action that enables the user to authenticate,
hopefully giving access to the resource.

=== login
Clients may request a login directly through a pre-defined endpoint, available for all ID providers. 
This provides a deterministic endpoint for accessing the login page of any ID provider.

The URL to the endpoint can be generated using the <<../libraries/lib-portal#loginurl, loginUrl() function in the portal library>>

[NOTE]
====
If the "login" endpoint is called with a "redirect" parameter, a validation of the origin is performed.
The result of this validation is then passed to the ID Provider as a request property "validTicket".
====


=== logout
Clients may request a logout directly through a pre-defined endpoint, available for all ID providers. 
This provides a deterministic endpoint for logging out of any ID provider.

The URL for this endpoint can be generated using the <<../libraries/lib-portal#logouturl, logoutUrl() function in the portal library>>

[NOTE]
====
If the "logout" endpoint is called with a "redirect" parameter, a validation of the origin is performed.
The result of this validation is then passed to the ID Provider as a request property "validTicket".
====


=== autoLogin

An ID provider may optionally include an AutoLogin filter. 
The purpose of this filter is to automatically sign in users, before they may access other parts of the execution pipeline.
This effectively blocks all unauthorised access attempts for the protected service.

If no user already exists in the context, the autoLogin filter is executed early in the request pipeline.

[NOTE]
====
image:xp-820.svg[XP 8.2.0,opts=inline] `autoLogin` runs for every ID provider on the request's virtual host that has the `autologin` <<#flows, flow>> enabled — the `default` provider first — until one of them authenticates the request or returns a response. In earlier versions only the `default` provider's `autoLogin` ran. Visit the https://developer.enonic.com/docs/platform/xp8/config/vhosts[vhost configuration] section for more details.
====

image:../../images/xp-820.svg[XP 8.2.0,opts=inline] A bearer token XP issued itself is accepted before `autoLogin` runs, on a vhost that enables the `autologin` flow for the user's ID provider and accepts the token's audience (one it declares, or XP's own issuer name on a vhost declaring none). `autoLogin` is then not called: the request is already authenticated, and the functions handling it see the user and <<request-response#access-token, `request.accessToken`>>. Any other bearer token reaches `autoLogin` untouched. See https://developer.enonic.com/docs/platform/stable/security/access-tokens[access tokens].

An ID provider that verifies a bearer token of its upstream identity system can pass the token on with the `accessToken` option of <<../libraries/lib-auth#login, `login()`>>. XP then applies the same rules as to its own tokens: the audience must be one the virtual host serves, and the scopes map to roles through the ID provider's scopes. The request then carries the token as `request.accessToken`. Verifying the token stays the ID provider's job.

[source,typescript]
----
import {login} from '/lib/xp/auth';

export function autoLogin(req: Request): void {
    const claims = verifyBearer(req); // the ID provider's own verification against its upstream
    if (!claims) {
        return;
    }
    login({
        user: claims.sub,
        idProvider: 'myIdProvider',
        skipAuth: true,
        scope: 'REQUEST',
        accessToken: {
            issuer: claims.iss,
            clientId: claims.azp ?? claims.client_id,
            scope: ([] as string[]).concat(claims.scp ?? claims.scope ?? []).flatMap((v) => v.split(' ')).filter(Boolean),
            audience: ([] as string[]).concat(claims.aud ?? [])
        }
    });
}
----

=== oauthConsent

image:../../images/xp-820.svg[XP 8.2.0,opts=inline] XP issues https://developer.enonic.com/docs/platform/stable/security/access-tokens[access tokens] to an ID provider's users through the OAuth device flow (https://datatracker.ietf.org/doc/html/rfc8628[RFC 8628]) and the authorization code flow with PKCE: a command-line tool, an MCP client or another application asks XP for access, the user signs in and approves, and the client receives XP-issued tokens. XP owns the protocols, the codes and the tokens; the page the user sees is the ID provider's, as the login page is. An ID provider that exports `oauthConsent` supports both flows; one that does not answers 404 on their endpoints, so a client is never handed a code it cannot complete.

`oauthConsent(req)` is called for `GET` and `POST` on `+/_/idprovider/<name>/device+` and `+/_/idprovider/<name>/authorize+`, once XP has done its part: the user is signed in (an unauthenticated request is answered with 401 and reaches the page again after the interactive login), the request has been looked up and checked, and a posted choice has been applied. The function renders a page for the state XP hands it in `req.oauthConsent` (<<../libraries/types#device-login, `OAuthConsent`>>, a union narrowed by `action`):

[%header,cols="1%,1%,98%a"]
[frame="none"]
[grid="none"]
|===
| Name | Type | Description
| idProvider | string | Name of the ID provider the page belongs to.
| action | string | What to show: `enter` (ask for the code the client displays), `confirm` (show the request and ask for approval), `done` (the request was approved or denied) or `wrongAccount` (the signed-in user belongs to another ID provider and cannot approve here).
| user | <<../libraries/types#oauth-consent-user, OAuthConsentUser>> | The signed-in user: `key`, `login`, `displayName`.
| error | string | *Optional.* On `enter`: why the previous code was refused. The only value so far is `+invalid_code+`; the page supplies the wording.
| flow | string | On `confirm`: `device` for device login, `code` for the authorization code flow.
| userCode | string | On `confirm` in device login: the code the client displays, so the user can check it matches.
| requestId | string | On `confirm` in the authorization code flow: the request the user decides on.
| clientId | string | On `confirm`: the client id the client sent.
| client | <<../libraries/types#oauth-consent-client, OAuthConsentClient>> | On `confirm`: the client's record: the name to show, its links, and whether XP knows it. A client registered with the ID provider, or one that registered itself, is `registered`; one that merely named itself is not, and its record repeats the id.
| scope | <<../libraries/types#oauth-consent-scope, OAuthConsentScope>>[] | On `confirm`: the scopes the client asked for, each with its `id`, the `title` and `description` the ID provider gave it, the `roles` it implies and whether it is `required`. Empty when the client asked for none.
| unrestricted | boolean | On `confirm`: `true` when the ID provider has no scopes, so an approved token carries the user's full memberships.
| audience | string[] | On `confirm`: the audiences the token will be for.
| csrf | string | On `confirm`: a per-session token the form must post back as `+_csrf+`.
| approved | boolean | On `done`: whether the user approved.
|===

The `confirm` page is a form that posts back to the same URL: `+user_code+` in device login or `request` in the authorization code flow, `approve` (`true` or `false`), `+_csrf+`, and one `scope` field per scope the user keeps. A scope left out is not granted, except a required one, which is granted whenever the request is approved; a scope that was never asked for is ignored. XP validates the posted choices; the page only renders. In device login the page shows the code, so the user can check it against the one on the device; the code flow has no code to show, and the browser is sent back to the client once the user has decided.

Scopes are worded by the ID provider that holds them (<<../libraries/lib-auth#createscope, `createScope()`>>), so the page shows `title` and `description` and falls back to the id; a title may be the whole wording. A client's name and links are its own words about itself: show them as text and plain links, nothing more.

.Minimal oauthConsent
[source,typescript]
----
import type {Request, Response} from '@enonic-types/core';

const escape = (value: string): string =>
    value.replace(/[&<>"']/g, (c) => ({'&': '&amp;', '<': '&lt;', '>': '&gt;', '"': '&quot;', "'": '&#39;'})[c] as string);

export function oauthConsent(req: Request): Response {
    const d = req.oauthConsent;
    if (!d) {
        return {status: 404};
    }
    if (d.action === 'confirm') {
        const scopes = d.scope
            .map(s => `<label><input type="checkbox" name="scope" value="${escape(s.id)}" checked ${s.required ? 'disabled' : ''}> ${escape(s.title)}</label>`)
            .join('');
        const required = d.scope
            .filter(s => s.required)
            .map(s => `<input type="hidden" name="scope" value="${escape(s.id)}">`)
            .join('');
        const reference = d.flow === 'code'
            ? `<input type="hidden" name="request" value="${escape(d.requestId!)}">`
            : `<p>Code: ${escape(d.userCode!)}</p><input type="hidden" name="user_code" value="${escape(d.userCode!)}">`;
        return {
            contentType: 'text/html',
            body: `<form method="post">
                <h1>Authorize ${escape(d.client.displayName)}</h1>
                ${reference}
                ${scopes}${required}
                <input type="hidden" name="_csrf" value="${d.csrf}">
                <button name="approve" value="true">Authorize</button>
                <button name="approve" value="false">Cancel</button>
            </form>`,
        };
    }
    if (d.action === 'done') {
        return {contentType: 'text/html', body: d.approved ? '<p>Request approved. You may close this window.</p>' : '<p>Request denied.</p>'};
    }
    if (d.action === 'wrongAccount') {
        return {contentType: 'text/html', body: `<p>${escape(d.user.displayName)} cannot approve requests for ${escape(d.idProvider)}.</p>`};
    }
    return {
        contentType: 'text/html',
        body: `<form method="get">${d.error ? '<p>That code was not recognised.</p>' : ''}
            <input name="user_code" placeholder="Enter code">
            <button>Next</button>
        </form>`,
    };
}
----

NOTE: A client's name is whatever it registered or sent, and a scope's wording is whatever its ID provider stored, so the example escapes them, and scope ids with them. A template engine that escapes by default does the same.


=== GET/POST etc

Additionally, an ID provider may also act as a regular <<request-response#, HTTP function>> — supporting any interaction as desired.
Communication with the implementation is handled via the ID provider endpoint.

The URL to this endpoint can be generated using the <<../libraries/lib-portal#idproviderurl, idProviderUrl() function in the portal library>>

[#flows]
== Flows

image:xp-820.svg[XP 8.2.0,opts=inline] A vhost mapping may restrict the flows an ID provider serves, with the provider's `flows` setting — e.g. `idProvider.myidp.flows = login,autologin`. XP itself enforces the three flows it manages:

login:: `handle401` and the `login` function.
autologin:: the `autoLogin` filter.
logout:: the `logout` function.

Any other name in the list addresses an *additional flow* of the ID provider application itself. XP dispatches the custom `GET`/`POST` functions regardless of the list, and instead hands the list to the implementation as `+request.idProviderSettings.flows+`, empty when no restriction applies. The property is absent when the vhost applies no flow restriction (and on XP versions before 8.2.0), so an absent list means every flow is enabled.

Use it to serve an endpoint only where its flow is listed. For example, an ID provider offering a device authorization flow can gate it on the name `device`:

[source,typescript]
----
import type {Request, Response} from '@enonic-types/core';

export function POST(request: Request): Response {
    const flows = request.idProviderSettings?.flows ?? [];
    if (flows.length > 0 && !flows.includes('device')) {
        return {status: 403};
    }
    // serve the device authorization endpoint
}
----

An administrator then enables the endpoint per vhost by listing the flow — `flows = autologin,device` — and disables it by leaving it out. Document the additional flows your ID provider supports, so administrators know what the names mean.
